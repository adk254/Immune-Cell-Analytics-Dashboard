# Immune Cell Population Analytics Dashboard

This repository contains a reproducible Python analysis pipeline and interactive dashboard for analyzing clinical-style immune cell population data.

The project loads immune cell count data from `cell-count.csv` into a SQLite database, calculates relative frequencies of immune cell populations, compares melanoma PBMC samples from miraclib responders and non-responders, and summarizes baseline subset results.

## Skills Demonstrated

- Reproducible Python analysis workflow
- SQLite database design for biological sample metadata and cell-count data
- Long-format data transformation and aggregation
- Statistical comparison of biological sample groups
- Multiple-testing correction with Benjamini–Hochberg FDR
- Interactive dashboard development with Streamlit and Plotly
- Clear communication of exploratory biological data analysis results

## Project Goal

The central analysis question is:

> Do melanoma patients who respond to miraclib have different immune-cell population frequencies than melanoma patients who do not respond?

To answer this, the analysis converts raw immune cell counts into relative frequencies within each sample, then compares those frequencies between responders and non-responders.

## How to Run

These commands work in GitHub Codespaces or any environment with Python 3.10+.

```bash
make setup      # Install dependencies
make pipeline   # Build database and run full analysis
make dashboard  # Launch the Streamlit dashboard
```

The pipeline creates `teiko_trial.db` in the repository root, runs all analyses, and saves outputs to `outputs/`.

## Database Schema

Two tables:

**`samples`** — one row per biological sample, storing all metadata: `sample` (primary key), `project`, `subject`, `condition`, `age`, `sex`, `treatment`, `response`, `sample_type`, and `time_from_treatment_start`.

**`cell_counts`** — one row per cell population per sample (long/normalized form). Each row stores `sample`, `population`, and `count`. Foreign-keyed to `samples`.

**Why this design?**
Separating metadata from measurements keeps the schema clean and avoids repeating subject-level data across every cell population row. The long format for `cell_counts` makes it easy to filter, aggregate, and join by population without needing to alter the schema when new cell types are added.

**How it scales:**
- Hundreds of projects and thousands of samples add rows, not columns — the schema handles this naturally.
- Indexes on `cell_counts(sample)`, `cell_counts(population)`, and a composite index on the most common filter columns in `samples` (condition, treatment, sample_type, response, time_from_treatment_start) keep queries fast at scale.
- The same schema works in PostgreSQL with minimal changes if the dataset outgrows SQLite.
- New cell populations, sample types, or metadata fields can be added without restructuring existing data.

## Code Structure

- **`load_data.py`** — Creates the SQLite schema and loads `cell-count.csv` into `teiko_trial.db` in the repository root. Intentionally standalone with no imports from `src/` so it can be run directly as required.
- **`analyze.py`** — Orchestrates the full analysis pipeline: frequency table, responder comparison, statistical tests, and baseline subset queries. Saves all outputs to `outputs/`.
- **`dashboard.py`** — Streamlit dashboard with four pages: Project Summary, Cell Frequencies, Responder Analysis, and Baseline Subset. Uses `@st.cache_data` to avoid re-querying on every interaction.
- **`src/analysis.py`** — Query functions that pull and transform data from the database into DataFrames.
- **`src/db.py`** — Single source of truth for the database path, shared by all modules.
- **`src/stats.py`** — Mann–Whitney U tests with Benjamini–Hochberg FDR correction across cell populations.
- **`src/plots.py`** — Plotly boxplot generation for the responder vs. non-responder comparison.

The `src/` module keeps analysis logic separate from orchestration scripts, making functions easy to test independently and reuse across both the pipeline and the dashboard without duplication.

## Cell-Type Frequency Summary

The pipeline calculates total cell count per sample by summing the five populations:

total_count = b_cell + cd8_t_cell + cd4_t_cell + nk_cell + monocyte

percentage  = count / total_count * 100

The result is saved as `outputs/cell_frequencies.csv` with columns: `sample`, `total_count`, `population`, `count`, `percentage`. It is also displayed in the dashboard under Cell Frequencies.

## Responder vs. Non-Responder Analysis

The analysis filters to melanoma PBMC samples from patients treated with miraclib, then compares immune-cell relative frequencies between responders (`response = yes`) and non-responders (`response = no`).

A two-sided Mann–Whitney U test was used because relative immune-cell frequencies may not be normally distributed. Benjamini–Hochberg FDR correction was applied across all five populations to reduce false positives from multiple testing. Results are saved as `outputs/responder_vs_nonresponder_stats.csv` and include:

- Sample counts per group
- Mean percentage per group
- Mean difference (responders minus non-responders)
- Unadjusted p-value
- FDR-adjusted p-value
- Significance flag at alpha = 0.05

**Main finding:** CD4 T cells showed the largest unadjusted difference between groups. Responders had a slightly higher average CD4 T-cell frequency (30.54%) than non-responders (29.90%), a difference of +0.64 percentage points (unadjusted p = 0.0133, FDR-adjusted p = 0.0667). After FDR correction, no immune-cell population was statistically significant at alpha = 0.05. Overall, the analysis suggests a possible CD4 T-cell signal worth follow-up, but does not provide strong corrected statistical evidence that any single measured population clearly distinguishes miraclib responders from non-responders.

## Limitations

This analysis is exploratory and based on the available sample metadata and five measured immune-cell populations. The results should not be interpreted as evidence of causation or as a validated predictive biomarker. Additional clinical variables, larger datasets, and independent validation would be needed before drawing stronger biological or clinical conclusions.
